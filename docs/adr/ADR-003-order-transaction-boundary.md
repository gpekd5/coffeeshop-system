# ADR-003: 주문 트랜잭션 경계

## 상태

제안됨

---

## 1. 배경

주문 생성은 장바구니, 메뉴, 포인트, 주문, 결제, 포인트 이력, 외부 이벤트 기록을 함께 다룬다.

이 중 일부만 성공하면 다음과 같은 데이터 불일치가 발생할 수 있다.

```text
포인트만 차감되고 주문이 없는 상태
주문은 있지만 결제 정보가 없는 상태
주문은 있지만 포인트 사용 이력이 없는 상태
주문은 완료됐지만 장바구니 항목이 남아 있는 상태
주문은 완료됐지만 Outbox Event가 없는 상태
```

따라서 주문 처리의 DB 변경 작업은 하나의 짧은 트랜잭션으로 묶고,
외부 네트워크 호출은 트랜잭션 밖에서 실행해야 한다.

---

## 2. 요구사항

주문 트랜잭션은 다음 조건을 만족해야 한다.

- 주문, 주문 항목, 결제, 포인트 차감, 포인트 이력은 원자적으로 처리한다.
- 주문 성공 후 장바구니 항목 삭제도 같은 트랜잭션에 포함한다.
- Outbox 모드에서는 주문 완료 Outbox Event 저장을 같은 트랜잭션에 포함한다.
- 포인트 부족, 메뉴 판매 불가, 장바구니 비어 있음 등 비즈니스 실패 시 전체를 Rollback한다.
- 외부 Mock API 호출과 Kafka Consumer의 외부 API 호출은 DB 트랜잭션에 포함하지 않는다.
- 동일 회원의 동시 주문에서도 포인트 초과 사용이 발생하지 않아야 한다.
- 동일 멱등키 요청은 중복 주문과 중복 결제를 만들지 않아야 한다.
- 여러 애플리케이션 인스턴스에서도 같은 결과를 보장해야 한다.

---

## 3. 고려한 대안

| 방식 | 설명 | 장점 | 단점 | 이번 프로젝트 적합성 |
|---|---|---|---|---|
| 단계별 개별 트랜잭션 | 포인트 차감, 주문 저장, 결제 저장을 각각 커밋한다. | 구현 단위가 작다. | 중간 실패 시 보상 트랜잭션이 필요하고 데이터 불일치 위험이 크다. | 부적합 |
| 하나의 긴 트랜잭션 | DB 변경과 외부 Mock API 호출까지 모두 한 트랜잭션에 넣는다. | 실패 시 한 번에 Rollback할 수 있어 보인다. | 외부 지연 동안 DB 락과 커넥션을 오래 점유하고 외부 장애가 주문 성공을 막을 수 있다. | 부적합 |
| DB 변경만 하나의 짧은 트랜잭션 | 정합성이 필요한 DB 변경만 묶고 외부 호출은 Commit 이후 실행한다. | 데이터 정합성과 짧은 락 점유를 함께 얻는다. | Commit 이후 동기 외부 호출 전 서버 종료 시 이벤트 유실 가능성이 있다. | 1차에 적합 |
| DB 변경 + Outbox를 하나의 트랜잭션 | 주문 데이터와 Outbox Event를 함께 저장하고 발행은 별도 처리한다. | 주문 완료 이벤트 유실 가능성을 줄이고 외부 장애와 주문 응답을 분리한다. | Outbox Publisher와 Kafka 운영 복잡도가 추가된다. | 2차에 적합 |
| 보상 트랜잭션 기반 처리 | 각 단계 실패 시 이전 단계의 반대 작업을 수행한다. | 외부 결제 등 긴 흐름에 확장할 수 있다. | 초기 범위 대비 복잡하고 보상 실패 시 복구가 어렵다. | 낮음 |

## 4. 결정

주문 생성은 **DB 변경 작업만 하나의 짧은 트랜잭션**으로 처리한다.

1차 동기 외부 전송 모드에서는 다음 순서를 사용한다.

```text
[트랜잭션]
멱등 주문 선조회
→ 장바구니 쓰기 잠금 조회
→ 장바구니 항목 조회 및 검증
→ 메뉴 읽기 잠금 조회
→ 메뉴 판매 상태 및 가격 검증
→ 포인트 쓰기 잠금 조회
→ 포인트 차감
→ 주문 저장
→ 주문 항목 저장
→ 결제 저장
→ 포인트 이력 저장
→ 장바구니 항목 삭제
→ Commit

[트랜잭션 밖]
외부 Mock API 동기 호출
→ 전송 결과 로그 저장
→ 주문 응답 반환
```

2차 Outbox 모드에서는 주문 트랜잭션 안에 Outbox Event 저장을 추가한다.

```text
[트랜잭션]
주문 저장
→ 결제 저장
→ 포인트 이력 저장
→ 장바구니 항목 삭제
→ Outbox Event 저장
→ Commit

[트랜잭션 밖]
Outbox Publisher
→ Kafka
→ Consumer
→ 외부 데이터 수집 플랫폼
```

## 5. 트랜잭션 안에 포함하는 작업

다음 작업은 하나의 논리적 주문 처리 결과를 구성하므로 같은 트랜잭션에 포함한다.

- 기존 멱등 주문 조회
- 장바구니 잠금 조회
- 장바구니 항목 조회 및 주문 가능 여부 검증
- 메뉴 잠금 조회 및 판매 상태, 가격 검증
- 포인트 잠금 조회 및 차감
- 주문 저장
- 주문 항목 저장
- 결제 저장
- 포인트 사용 이력 저장
- 주문 성공 후 장바구니 항목 삭제
- Outbox 모드의 주문 완료 Outbox Event 저장

이 중 하나라도 실패하면 전체 트랜잭션을 Rollback한다.

---

## 6. 트랜잭션 밖에서 처리하는 작업

다음 작업은 네트워크 지연이나 외부 장애가 발생할 수 있으므로 주문 DB 트랜잭션에 포함하지 않는다.

- 외부 Mock API 동기 호출
- Kafka 발행
- Kafka Consumer의 외부 데이터 수집 API 호출
- 운영 모니터링 조회
- 장시간 대기 또는 재시도 작업

외부 Mock API 호출 실패나 Timeout은 이미 Commit된 주문을 Rollback하지 않는다.
대신 전송 결과를 별도 로그 또는 Outbox/Kafka 처리 상태로 남긴다.

---

## 7. 잠금 순서

주문 트랜잭션은 모든 요청에서 다음 잠금 순서를 유지한다.

```text
장바구니
→ 메뉴 ID 오름차순
→ 포인트
```

잠금 순서를 고정해 서로 다른 요청이 같은 리소스를 다른 순서로 잠그면서 발생하는 Deadlock 가능성을 줄인다.

포인트는 MySQL 비관적 쓰기 락을 우선 사용한다.
메뉴는 주문 검증 중 가격과 판매 상태 변경이 섞이지 않도록 비관적 읽기 락을 사용한다.
장바구니는 주문 중 수량 변경과 삭제를 막기 위해 비관적 쓰기 락을 사용한다.

---

## 8. 멱등성과 Unique 제약

주문 요청은 `Idempotency-Key` Header를 사용한다.

```text
UNIQUE(member_id, idempotency_key)
```

일반 재요청은 트랜잭션 초기에 기존 주문을 조회해 기존 결과를 반환한다.

동시 요청에서 두 트랜잭션이 모두 기존 주문을 찾지 못할 수 있으므로,
DB Unique 제약을 최종 방어선으로 사용한다.
Unique 충돌이 발생하면 기존 주문을 다시 조회해 동일한 주문 결과를 반환한다.

---

## 9. Rollback 기준

다음 상황에서는 주문 트랜잭션 전체를 Rollback한다.

- 회원을 찾을 수 없음
- 장바구니를 찾을 수 없음
- 장바구니가 비어 있음
- 장바구니 항목 수량이 올바르지 않음
- 메뉴를 찾을 수 없음
- 메뉴가 판매 중이 아님
- 포인트 계정을 찾을 수 없음
- 포인트 잔액 부족
- 주문 저장 실패
- 주문 항목 저장 실패
- 결제 저장 실패
- 포인트 이력 저장 실패
- 장바구니 항목 삭제 실패
- Outbox Event 저장 실패

Rollback 후에는 포인트 차감, 주문, 주문 항목, 결제, 포인트 이력, 장바구니 삭제가 일부만 남아서는 안 된다.

## 10. 예상 단점과 위험

### 10.1 트랜잭션 책임이 커질 수 있다

주문은 여러 도메인을 조합하므로 트랜잭션 서비스가 커질 수 있다.
이를 줄이기 위해 Controller는 요청과 응답에 집중하고,
Facade는 멱등성 및 외부 전송 순서를 조정하며,
TransactionService는 DB 정합성 작업만 담당한다.

### 10.2 락 대기와 Deadlock

동일 회원 주문은 포인트 행을 순차 처리하므로 락 대기가 발생할 수 있다.
트랜잭션 안에서는 외부 호출을 하지 않고, 잠금 순서를 고정해 대기 시간과 Deadlock 위험을 줄인다.

### 10.3 1차 동기 전송의 이벤트 유실 가능성

1차 모드에서는 주문 Commit 이후 외부 Mock API 호출 전 서버가 종료되면 이벤트가 유실될 수 있다.
이 한계는 2차 Outbox 모드에서 주문과 Outbox Event를 같은 트랜잭션에 저장해 줄인다.

## 11. 검증 계획

### 정상 주문

예상 결과:

- 주문이 `COMPLETED`로 저장된다.
- 주문 항목, 결제, 포인트 이력이 저장된다.
- 포인트가 주문 금액만큼 차감된다.
- 장바구니 항목이 삭제된다.
- Outbox 모드에서는 Outbox Event가 저장된다.

### 포인트 부족

예상 결과:

- 주문이 생성되지 않는다.
- 결제와 포인트 이력이 생성되지 않는다.
- 포인트 잔액이 변경되지 않는다.
- 장바구니 항목이 유지된다.

### 저장 단계 실패

주문 저장, 결제 저장, 포인트 이력 저장, 장바구니 삭제, Outbox 저장 실패를 각각 재현한다.

예상 결과:

- 전체 트랜잭션이 Rollback된다.
- 포인트 잔액, 주문, 결제, 포인트 이력, 장바구니 항목이 서로 불일치하지 않는다.

### 동일 회원 동시 주문

예상 결과:

- 포인트가 음수가 되지 않는다.
- 성공 주문 수와 결제, 포인트 이력 수가 일치한다.
- 실패 주문의 부분 데이터가 남지 않는다.

### 동일 멱등키 동시 요청

예상 결과:

- 주문은 한 건만 생성된다.
- 포인트는 한 번만 차감된다.
- 모든 성공 응답은 같은 주문 결과를 반환한다.

### 외부 Mock API 실패

예상 결과:

- 주문 DB 데이터는 유지된다.
- 외부 전송 실패 로그가 기록된다.
- DB 트랜잭션 Rollback은 발생하지 않는다.

## 12. 최종 결정 요약

| 항목 | 결정 |
|---|---|
| 주문 DB 변경 | 하나의 짧은 트랜잭션 |
| 외부 Mock API 호출 | Commit 이후 트랜잭션 밖에서 실행 |
| Outbox Event 저장 | Outbox 모드에서 주문 트랜잭션에 포함 |
| Kafka 발행 및 Consumer 외부 호출 | 트랜잭션 밖에서 실행 |
| 잠금 순서 | 장바구니 → 메뉴 ID 오름차순 → 포인트 |
| 포인트 잠금 | MySQL 비관적 쓰기 락 |
| 멱등성 최종 방어 | `(member_id, idempotency_key)` Unique 제약 |
| Rollback 기준 | DB 정합성 작업 중 하나라도 실패하면 전체 Rollback |
